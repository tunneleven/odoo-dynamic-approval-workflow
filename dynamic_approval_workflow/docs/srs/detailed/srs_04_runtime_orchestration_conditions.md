# SRS-04 Runtime Orchestration and Conditions

Version: `v1.1-draft`  
Date: `2026-02-27`  
Parent: `dynamic_approval_workflow_srs_v1.3.md`  
Master Traceability: `srs_00_master_traceability.md`

## 1. Purpose
Define deterministic runtime behavior for workflow execution: token progression, routing conditions, parallel and quorum joins, rework loops, simulation behavior, timeout auto-decisions, and incident/cancellation runtime effects.

## 2. Scope
In scope:
1. Runtime orchestration semantics for sequential and parallel paths.
2. Condition evaluation at gateways and sequence transitions.
3. Join behavior (`all`, `any`, `quorum`) and quorum threshold computation.
4. Rework loop handling, including rework in parallel contexts.
5. Timeout auto-decision policy execution.
6. Simulation/dry-run behavior used as pre-publish quality gate.
7. Runtime cancellation and incident recovery semantics.

Out of scope:
1. Approver identity resolution and delegation assignment details (`SRS-05`).
2. UI/modeler authoring behavior (`SRS-03`).
3. Binding authorization policy (who can cancel/trigger) (`SRS-02`).

## 5. Runtime Model
### 5.1 Core Runtime Objects
1. `instance`
- Workflow execution for one business record.
2. `node_runtime`
- Runtime status per BPMN node for the instance.
3. `token`
- Branch progress marker through sequence flows.
4. `decision_event`
- User/system decision input that may advance runtime.

### 5.2 Instance States (Operational Semantics)
1. `running`
- Transitional processing state while engine is executing a runtime tick.
- Not a long-lived waiting state.

2. `waiting_human`
- At least one pending human decision task exists.
- This state has precedence over `waiting_timer` when both human task(s) and timer(s) are present.

3. `waiting_timer`
- No human decision is pending.
- Instance is blocked only by timer/event wait (scheduled delay, timer gateway, timed checkpoint).

4. `completed_approved`
- Terminal success outcome reached.

5. `completed_rejected`
- Terminal rejection outcome reached.

6. `cancelled`
- Instance terminated by user/admin policy before terminal approval/rejection.

7. `error_incident`
- Instance halted due to runtime/configuration/policy error requiring intervention.

### 5.2.1 State Precedence Rule
When multiple wait conditions exist, resolve instance state in this order:
1. `error_incident` (if incident is open and blocks progression)
2. terminal states (`completed_approved`, `completed_rejected`, `cancelled`)
3. `running` (only during active runtime tick)
4. `waiting_human` (if any open human task exists)
5. `waiting_timer` (only if no open human task exists and timer wait is pending)

### 5.2.2 Typical Transitions
| From | Trigger | To |
|---|---|---|
| `running` | Human task created | `waiting_human` |
| `waiting_human` | Reminder timer fires, task still open | `running` -> `waiting_human` |
| `waiting_human` | Human task resolved, timer-only gate remains | `running` -> `waiting_timer` |
| `waiting_timer` | Timer expires and creates human task | `running` -> `waiting_human` |
| `waiting_timer` | Timer expires and flow reaches terminal approve | `running` -> `completed_approved` |
| `running` | Terminal rejection path selected | `completed_rejected` |
| `waiting_human` | Policy-authorized cancel request | `running` -> `cancelled` |
| `waiting_timer` | Policy-authorized cancel request | `running` -> `cancelled` |
| `error_incident` | Admin resolves and retries | `running` |
| `error_incident` | Admin cancels instance | `cancelled` |
| any non-terminal | Runtime error/ambiguous route/impossible quorum | `error_incident` |

### 5.2.3 Clarification Example
A manager approval task with 24-hour reminder and 48-hour escalation remains `waiting_human` while the task is pending.
When reminder/escalation timer fires, state briefly becomes `running` for processing, then returns to `waiting_human` if a human task is still pending.
Only timer-only waits (with no pending human task) are `waiting_timer`.

### 5.3 Node State Machine
Node states:
1. `pending`
2. `active`
3. `completed`
4. `timed_out`
5. `skipped`

Node transition table:
| From | Trigger | To | Preconditions | Notes |
|---|---|---|---|---|
| `pending` | Token arrives and activation criteria met | `active` | Node reachable and not cancelled/skipped | Activation event emitted |
| `active` | Human/system decision resolves node | `completed` | Completion criteria met | Standard completion |
| `active` | Timeout policy executes | `timed_out` | Timer valid and node still active | `timed_out` is terminal node state |
| `active` | Branch superseded / route not selected | `skipped` | Join/route policy dictates skip | No further work on this node |
| `pending` | Branch superseded before activation | `skipped` | Join/route policy dictates skip | No activation occurs |

Node invariants:
1. `completed`, `timed_out`, and `skipped` are terminal node states.
2. Rework does not mutate terminal node states; it creates new `node_runtime` records.

### 5.4 Token Lifecycle
### 5.4.1 Token Data Contract
Minimum token fields:
1. `token_id`
2. `instance_id`
3. `branch_id`
4. `parent_token_id` (nullable)
5. `current_node_runtime_id`
6. `state` (`active`, `consumed`, `cancelled`)
7. `created_at_utc`
8. `closed_at_utc` (nullable)
9. `close_reason_code` (nullable)

### 5.4.2 Token Transition Rules
1. Sequential advance consumes current token and creates downstream token.
2. Parallel split creates one child token per active outgoing branch.
3. `all` join consumes participating branch tokens when completion rule is met.
4. `quorum` join consumes qualifying tokens and resolves per quorum policy.
5. `any` join:
- First qualifying branch token completes join.
- Remaining `active` branch tokens transition to `cancelled` with `close_reason_code = branch_superseded`.
- Related `pending/active` node_runtimes transition to `skipped`.
- Related `pending/active` human tasks are cancelled with reason `branch_superseded` and approvers notified.
- Pending timers on cancelled branches are deactivated.

### 5.4.3 Token Persistence Rule
Tokens are audit artifacts and are never hard-deleted by runtime operations.

## 6. Execution State Machine
### 6.1 Transition Triggers
1. `instance.started`
2. `task.decision.received`
3. `timer.expired`
4. `signal.received`
5. `cancel.requested`
6. `system.retry`

### 6.2 Deterministic Runtime Tick
For each accepted trigger:
1. Acquire per-instance serialization lock.
2. Load active nodes and tokens.
3. Evaluate node completion and guard conditions.
4. Resolve outgoing path(s) via gateway/condition semantics.
5. Create next node activations and tasks/timers.
6. Persist state transition atomically.
7. Emit audit and integration events.

### 6.3 Sequential Semantics
1. One active token advances to exactly one next node unless gateway rules open multiple paths.
2. Node completion is prerequisite for downstream activation.

### 6.4 Parallel Semantics
1. Split gateway emits one token per active outgoing branch.
2. Branch tokens progress independently.
3. Join node evaluates branch completion according to configured join rule.

### 6.5 Signal Semantics
1. Supported signal categories: `manual_signal`, `external_message`, `system_signal`.
2. Signal matching keys: `(instance_id, signal_name)`.
3. Signals are consumable only by nodes configured as signal/message wait nodes.
4. Unknown or non-matching signals are ignored with audit warning event.

### 6.6 Incident Resolution Semantics
1. Incident is raised when runtime cannot continue deterministically.
2. Admin may:
- apply corrective action and trigger `system.retry`
- cancel instance
3. Retry resumes from failed runtime context snapshot.
4. Repeated failure beyond retry policy threshold returns to `error_incident` and escalates.

## 7. Condition Evaluation Rules
### 7.1 Evaluation Inputs
1. Canonical record snapshot.
2. Workflow runtime context (instance, step metadata, actor/system context).
3. Compiled condition metadata from publish step.

### 7.2 Evaluation Order
1. Static rule clauses from no-code builder.
2. Optional admin snippet clause (if enabled for condition).
3. Final boolean expression composition (`AND`/`OR`/grouping) as compiled.

### 7.3 Determinism Rules
1. Condition evaluation must be side-effect free.
2. Evaluation result for same context/version must be repeatable.
3. Snippet failure/timeout/violation resolves as fail-safe false.

### 7.4 Path Selection Rules
1. Exclusive path: first true path by deterministic sequence priority.
2. Multiple true paths in exclusive gateway => configuration error at validation stage.
3. No true path => apply explicit default path; if none, set incident and halt instance progression.

### 7.5 Condition Runtime Contract
Runtime expects compiled condition metadata as deterministic JSON rule tree:
1. Node shape:
- `connector`: `AND` or `OR`
- `rules`: list of nested rule/group objects
2. Rule shape:
- `field_path`
- `operator`
- `value`
- `value_type`
3. Minimum operator set:
- `eq`, `neq`, `in`, `not_in`, `gt`, `gte`, `lt`, `lte`, `contains`, `starts_with`, `is_set`, `is_empty`
4. Null/missing field policy:
- Missing/null evaluates `False` except `is_empty` which evaluates `True`.
5. Type coercion policy:
- No implicit string-to-number coercion; type mismatch evaluates `False` and logs warning.
6. Relational traversal policy:
- Maximum depth of 3 relationship hops.
7. Ownership boundary:
- Builder/schema ownership is in `SRS-03` and `SRS-10`; SRS-04 defines runtime consumption contract.

## 8. Join and Quorum Resolution
### 8.1 Join Modes
1. `all`
- Wait until all required branch tokens reach join.
2. `any`
- Complete join when first qualifying branch completes.
- Qualifying outcome set is configurable per join: `approve_only` (default), `reject_only`, `any_outcome`.
3. `quorum`
- Complete join when required threshold is reached.

### 8.2 Quorum Computation
1. Absolute mode
- Required approvals = configured integer `q_abs`.
2. Percentage mode
- Required approvals = `ceil(total_eligible * q_pct)`.
3. Optional minimum floor
- Final required approvals = `max(computed_required, floor_abs)`.

### 8.3 Eligible Set Snapshot Policy
1. Default policy: `freeze_at_assignment`.
- Eligible population is snapshotted when step activates.
2. Optional policy: `recompute_on_event`.
- Eligible population recalculates on relevant assignee-set changes.
3. Policy used must be recorded in audit payload for deterministic replay.

### 8.4 Quorum Outcome Resolution
1. Approval quorum can close step early when met.
2. Optional rejection quorum may be configured per step.
3. Mixed outcome handling:
- If approval quorum met first => approval outcome.
- If rejection quorum met first => rejection outcome.
4. Dynamic impossibility detection:
- If remaining eligible cannot satisfy outstanding required approvals/rejections, raise incident.
5. Timeout auto-decisions count toward quorum by default (configurable per step).

## 9. Timeout Auto-Decision Matrix
### 9.1 Policies
1. `auto-approve`
- System records timeout reason and advances with approval outcome where policy allows.
2. `auto-reject`
- System records timeout reason and transitions to rejection path.
3. `escalate-only`
- System escalates/alerts but does not close decision automatically.

### 9.2 Timeout Execution Sequence
1. Timer reaches deadline.
2. Runtime revalidates node still pending.
3. Apply configured timeout policy.
4. Record decision reason code `timeout_<policy>`.
5. Persist transition and emit notifications/events.

### 9.3 Safety Rules
1. Timeout policy execution must be idempotent.
2. Expired timer on already-closed or superseded node_runtime becomes no-op with audit note.

### 9.4 Timeout Configuration Scope
1. Timeout duration is configured per step.
2. Timer mode default is calendar-time.
3. Business-hours timer mode is a future enhancement.
4. Reminder/escalation schedule ownership is in `SRS-05`.

## 10. Rework Loop Behavior
### 10.1 Rework Target Configuration
1. Rework targets are configured at design time in process definition.
2. Runtime-selected ad-hoc rework targets are out of scope.

### 10.2 Loop Guard Policy
1. Default maximum loop count: `5`.
2. Configurable range: `1..99` per step.
3. Exceeding loop cap triggers incident and admin path.

### 10.3 Rework in Parallel Context
1. Rework from a branch to a target before the parallel split cancels sibling branches and rewinds to target.
2. Rework to target inside same branch rewinds only that branch path.
3. Rework creates new `node_runtime` records for re-entered path segments.
4. Approver resolution re-runs for re-activated human steps (details in `SRS-05`).
5. Record snapshot is refreshed when rework path re-enters target node.

### 10.4 Rework Payload and Tracking
1. Rework decision includes mandatory `change_request_notes`.
2. Instance maintains `loop_iteration` counter.
3. Audit events capture rework origin node, target node, and iteration.

## 11. Simulation and Dry-Run
### 11.1 Simulation Context Inputs
1. Designer-provided synthetic context records (JSON).
2. Optional sampled records from real data with redaction policy.

### 11.2 Execution Model
1. Simulation runs non-destructive execution against selected contexts.
2. Human task outcomes are represented by synthetic decision vectors.
3. Condition/snippet rules run under same policy constraints as runtime.

### 11.3 Coverage Metrics
1. `node_coverage_pct`
2. `branch_coverage_pct`
3. `unreachable_nodes[]`
4. `dead_ends[]`
5. `ambiguous_gateways[]`

### 11.4 Publish Blocking Rules
Publish is blocked when any of the following occurs:
1. Dead-end detected in supported executable path.
2. Required node is unreachable.
3. Ambiguous exclusive gateway remains unresolved.
4. Condition/snippet evaluation integrity check fails.

### 11.5 Simulation Report Contract
Minimum report structure:
`{ passed, node_coverage_pct, branch_coverage_pct, unreachable_nodes, dead_ends, ambiguous_gateways, warnings, contexts_executed }`

### 11.6 Simulation Performance Constraint
Simulation run must complete within configured execution budget; budget breach is reported and blocks publish when policy marks simulation as mandatory gate.

## 12. Consistency and Performance Controls
### 12.1 Strong Consistency (Single Record)
1. One serialized mutation path per instance transition commit.
2. Concurrent decisions on same step resolve via deterministic winner and conflict/no-op handling.

### 12.2 Latency Budget (`NFR-002`)
1. Budget window starts at decision acceptance.
2. Budget ends at durable state commit plus notification enqueue.
3. P95 target must remain under 2 seconds.

### 12.3 Deterministic Conflict Rules
1. Duplicate decision on already-closed task => no-op with stable response.
2. Concurrent quorum-reaching decisions => exactly one join completion event committed.
3. Cancel request arriving during active tick is queued and applied after current tick commit.

### 12.4 Concurrency Control Requirements
1. Runtime must enforce per-instance serialization for each mutation tick.
2. Lock acquisition must have timeout and bounded retry with backoff.
3. If lock cannot be acquired within retry budget, raise incident.
4. Lock window must not include external dispatch operations.
5. Concrete lock mechanism is implementation design concern and must satisfy these behavioral constraints.
